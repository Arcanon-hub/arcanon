# Requirements: Arcanon — v0.2.0 Scan Persistence, Pipeline & Security Hardening

**Defined:** 2026-06-29
**Core Value:** Understand and protect your architecture across repositories — keep the map current automatically, with a lean and trustworthy command surface.

Requirements for the v0.2.0 milestone, grouped by the four issue tracks (#49–#52).
Dependency order: **SEC (#51)** is independent and sequences early; **ISO (#49)** is
the foundation; **PIPE (#50)** depends on ISO; **INTG/PERF (#52)** depend on ISO+PIPE.

## v1 Requirements

### Security — issue #51 (independent; sequence early)

- [x] **SEC-01**: MCP `queryChanged()` resolves changed files without a shell — `commit_range` is passed to git as `execFileSync`/argv values, never interpolated into a command string.
- [x] **SEC-02**: OpenAPI comparison passes spec paths to `oasdiff` as argv values (never quoted shell fragments) at every call site (`oasdiff breaking`, `oasdiff diff`).
- [x] **SEC-03**: Git revision/range inputs are validated and option-injection is rejected (e.g. `--` separators); inputs containing shell metacharacters cannot execute commands and are passed literally or rejected. Tests cover a hostile `commit_range` and quote/metacharacter-containing spec paths.
- [x] **SEC-04**: Hub queue rows persist an immutable destination at enqueue time — Hub URL and organization ID (and a documented decision on binding to a key fingerprint vs URL/org).
- [x] **SEC-05**: `drainQueue()` uploads each row to its stored destination; switching organizations after enqueue cannot cause an existing queued upload to be sent to the new org.
- [x] **SEC-06**: Legacy queue rows (without a bound destination) are migrated safely or held for explicit user action — never silently retargeted.
- [x] **SEC-07**: Non-retriable 4xx responses transition a queue row to `dead` in a single drain attempt; queue status counters match persisted row state.
- [x] **SEC-08**: Response bodies and payload fragments that may contain source evidence are not logged.

### Persistence & Isolation — issue #49 (foundation)

- [x] **ISO-01**: Two project roots opened in the same worker use different database handles and cannot read or write each other's data (no process-global DB singleton).
- [x] **ISO-02**: Database handles are served by a factory/pool keyed by canonical project identity, with correct cache behavior on repeated resolution.
- [x] **ISO-03**: A complete scan (begin → persist findings → apply overrides → reconcile stale data → end) executes as one transactional unit of work; a forced failure at any point rolls back the entire scan.
- [x] **ISO-04**: A scan version is marked completed only after all cleanup/reconciliation finishes (no completed bracket with pending cleanup).
- [x] **ISO-05**: All cleanup is scoped by project/repo ownership — scanning repo A cannot delete or modify repo B's schemas or secondary state.
- [x] **ISO-06**: An explicit history model is in place (append-only versioned graph rows or immutable snapshot databases) so two completed scans retain enough data for an accurate added/removed/modified diff.
- [x] **ISO-07**: `/arcanon:diff HEAD~1 HEAD` and graph drift produce correct results against retained history.
- [x] **ISO-08**: Removed endpoints, actors, dependencies, and metadata disappear after a successful full scan (all child/secondary state is reconciled or versioned, not only inserted/upserted).
- [x] **ISO-09**: A project-level map/run identifier groups all repo scans from one mapping operation into one atomic project version.
- [x] **ISO-10**: Failure recovery is defined for abandoned/incomplete scans (no permanently half-written graph state).
- [x] **ISO-11**: Integration tests exercise real pool resolution and real multi-project databases (not mocked resolvers).

### Pipeline & Contract — issue #50 (depends on ISO)

- [x] **PIPE-01**: `/arcanon:map`, `/arcanon:rescan`, MCP `impact_scan`, and HTTP scan requests invoke the same `ScanService` pipeline; commands and transports are thin adapters with no duplicated persistence/reconciliation logic.
- [x] **PIPE-02**: MCP `impact_scan` returns the actual HTTP/pipeline failure (honors `response.ok`) instead of reporting false `triggered` success.
- [x] **PIPE-03**: Pending corrections are applied exactly once on the next successful map or rescan — `/arcanon:map` applies them, and `/arcanon:rescan` no longer throws when pending overrides are evaluated.
- [x] **PIPE-04**: Incremental scans preserve unchanged findings and correctly remove findings owned by deleted/renamed files (no full-snapshot deletion from a changed-files-only report).
- [x] **CTR-01**: One canonical, executable contract defines crossing values, protocols, source locations, schemas, and evidence; all paths validate against it.
- [x] **CTR-02**: Schema findings carry an explicit connection identity and are persisted only against that connection (no attach-to-every-connection).
- [x] **CTR-03**: `source_file` and optional symbol/line information are separate fields in the contract and persistence layer.
- [x] **CTR-04**: Every public persistence entry point validates findings before writes (no direct `persistFindings()` with unvalidated input).
- [x] **CTR-05**: End-to-end tests exercise each transport (command, MCP, HTTP) against the real pipeline.

### Integrations Correctness — issue #52 (depends on ISO + PIPE)

- [x] **INTG-01**: `/arcanon:drift graph` executes successfully against two real retained versions — drift SQL references real columns (`scan_versions.started_at`/`completed_at`, `target_service_id`) and routes through the canonical version/diff API.
- [x] **INTG-02**: A successful (transactionally completed) scan updates semantic search; removed services/endpoints are removed from Chroma — Chroma sync lives in the scan-completion path, not a disconnected `writeScan()` caller.
- [x] **INTG-03**: Chroma records are namespaced by project (and repo/service/endpoint) so identical service names across projects do not overwrite each other; results are scoped to the requested project.
- [x] **INTG-04**: UI filtering never renders an edge whose required endpoint is filtered out, and invisible nodes are consistently excluded (not drawn dimmed).

### Scaling & Runtime — issue #52 (perf hardening; after correctness)

- [x] **PERF-01**: Large maps have documented latency/memory targets, with response limits/pagination or graph summaries so `getGraph()` does not serialize an unbounded payload.
- [x] **PERF-02**: `detectMismatches()` and actor-connection lookups are batched (no per-connection / per-actor N+1); evidence validation caches source-file contents within a run; type-drift traversal does not reread trees per shared type.
- [x] **PERF-03**: Query-plan tests confirm indexes exist for upstream-impact and scan-version access patterns (including target-side lookups).
- [x] **PERF-04**: Multi-repo agent scanning uses bounded, configurable concurrency (not unbounded `Promise.allSettled(map())`), and the bound is tested.
- [x] **PERF-05**: The DB pool has lifecycle management — idle eviction and close-on-shutdown — so no project database handles remain open indefinitely.
- [x] **PERF-06**: Fastify routes do not block the event loop on synchronous SQLite/filesystem operations (async or offloaded to a worker/background task where latency can exceed interactive budgets).

## Future Requirements (deferred)

- Editor-client scan transport (the unified pipeline should make this cheap, but it is not in v0.2.0 scope).
- Background/worker offload for expensive drift/file traversal beyond what PERF-06 requires for interactive latency.

## Out of Scope

| Feature | Reason |
|---------|--------|
| v0.2.0 "Skills & Agents" layer | Deferred — this milestone is persistence/pipeline/security hardening; the skills layer is a separate future milestone. |
| New scan capabilities / detectors | This milestone fixes the existing pipeline's correctness and safety; no new detection features. |
| Hub server-side changes | Plugin-side only; Hub `X-Org-Id`/whoami enforcement (THE-1030) is tracked separately. |
